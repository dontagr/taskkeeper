# Матрица задач: когда отдавать ИИ (dev / QA)

Артефакт к книге **«Вайбкодер, или как подружиться с ИИ»** (глава 8).  
Сквозной пример кода — [Task keeper](../README.md) в этом репозитории.

**Как читать таблицу**

| Метка | Значение |
|-------|----------|
| **Да** | ИИ обычно ускоряет; риск низкий при вашей проверке |
| **Осторожно** | Имеет смысл, но нужны контекст, ревью, тесты или лимиты |
| **Нет** | Часто дороже по времени/риску, чем делать самому или с ментором |

**Оси (из книги):** риск ошибки × глубина контекста продукта. Ниже — практическая раскладка по типовым задачам.

**Правило по умолчанию:** ИИ делает **черновик**, человек — **источник правды**, **ревью** и **ship**.

## Разработка (backend / frontend / fullstack)

| Задача | ИИ | Почему / что проверить |
|--------|-----|------------------------|
| Объяснить ошибку из stack trace | **Да** | Низкий риск; сверить с докой и реальным кодом |
| Написать unit-тест к уже существующей функции | **Да** | Дать сигнатуру, примеры, граничные случаи; прогнать тесты |
| Сгенерировать boilerplate (DTO, mapper, OpenAPI stub) | **Да** | Сверить с конвенциями проекта |
| Регулярки, парсинг простого формата | **Да** | Прогнать на edge cases вручную |
| Рефакторинг переименования в одном модуле | **Да** | Малый scope; прогнать тесты |
| Добавить логирование / метрики по шаблону команды | **Да** | Проверить PII и cardinality |
| Написать README / комментарии к публичному API | **Да** | Факты сверить с кодом |
| Черновик SQL (SELECT, миграция по описанию) | **Осторожно** | EXPLAIN, staging, бэкап; не доверять «оптимально» |
| Рефакторинг через несколько пакетов / сервисов | **Осторожно** | Большой дифф; пошагово, тесты после каждого шага |
| Интеграция с незнакомым SDK | **Осторожно** | Версии API устаревают; сверить с официальной докой |
| Починить падающий CI без понимания причины | **Осторожно** | Дать лог; не применять «fix» вслепую |
| Оптимизация производительности | **Осторожно** | Нужны профили и метрики, не советы «на глаз» |
| Дизайн схемы БД с нуля | **Осторожно** | ИИ не знает нагрузку и эволюцию домена |
| Выбор архитектуры (монолит / микросервисы / очереди) | **Осторожно** | Brainstorm — да; решение — за командой и метриками |
| Реализация auth / OAuth / сессий | **Осторожно** | Только по спеке и проверенным библиотекам; security review |
| Работа с чужим legacy без тестов | **Осторожно** | Маленькие шаги; сначала тесты-страховка |
| Криптография «с нуля» (свой cipher, nonce logic) | **Нет** | Использовать проверенные библиотеки и аудит |
| Платежи, биллинг, идемпотентность денег | **Нет** | Домен + compliance; ИИ — только черновик под ревью эксперта |
| Прод-инцидент под нагрузкой | **Нет** | Runbook, on-call, откат; ИИ — после стабилизации для постмортема |
| Единственный источник правды о бизнес-правилах | **Нет** | Спросить аналитика/лида; ИИ галлюцинирует домен |
| Деплой / изменение prod config без чеклиста | **Нет** | Только процесс команды |
| Копипаста большого диффа в прод без ревью | **Нет** | Всегда ревью + CI |

## Тестирование (manual / automation / SDET)

| Задача | ИИ | Почему / что проверить |
|--------|-----|------------------------|
| Сгенерировать чек-лист по user story | **Да** | Дополнить граничными случаями из опыта |
| Написать тест-кейсы в таблице (шаг / ожидание) | **Да** | Приоритизация и риски — за тестировщиком |
| Черновик bug report по скрину/логу | **Да** | Шаги воспроизведения проверить вручную |
| Параметризация данных для тестов | **Да** | Валидность данных и PII |
| Скелет автотеста (Playwright, Cypress, pytest) | **Да** | Селекторы и стабильность — под ваш UI |
| Mock/stub для изолированного API-теста | **Да** | Контракт mock = реальный API |
| Тест-план для релиза (smoke / regression scope) | **Осторожно** | ИИ не знает реальный diff релиза без контекста |
| Автотесты на UI без page object / стабильных локаторов | **Осторожно** | Flaky-тесты хуже, чем их нет |
| «Покрой всё E2E» по описанию фичи | **Осторожно** | Пирамиду тестов задаёт команда |
| Нагрузочное тестирование (сценарии, пороги) | **Осторожно** | Нужны SLO и реальные профили нагрузки |
| Security-тесты (инъекции, IDOR) | **Осторожно** | Чеклисты OWASP — ориентир; не замена пентесту |
| Решение «баг или фича» по одному скрину | **Осторожно** | Нужен продукт и спека |
| Подписать «готово к релизу» без прогона | **Нет** | Ответственность тестировщика/команды |
| Игнорировать exploratory из-за «ИИ всё покрыл» | **Нет** | ИИ не заменяет исследовательское тестирование |
| Автотесты на прод-данные / реальные PII | **Нет** | Политики и маскирование |

## Общее для dev и QA

| Задача | ИИ | Почему / что проверить |
|--------|-----|------------------------|
| Выучить концепт (REST, git rebase, контракт-тест) | **Да** | Проверить на официальной доке |
| Сравнить два подхода (таблица плюсов/минусов) | **Да** | Не принимать как финальное решение |
| Написать commit message / PR description | **Да** | Факты из реального диффа |
| Code review чужого PR (вопросы, замечания) | **Да** | Не заменяет ревью человека |
| Review **своего** кода от ИИ | **Осторожно** | Слепое доверие; смотреть diff построчно |
| Перевод технической документации | **Осторожно** | Термины и версии |
| Генерация данных с секретами в промпте | **Нет** | Утечка в логи провайдера |
| Вставить API keys / prod URL в чат | **Нет** | Политика компании и риск утечки |

## По фазе работы (цикл вайбкодинга)

| Фаза | ИИ | Комментарий |
|------|-----|-------------|
| Постановка задачи, уточнение AC | **Да** | Черновик вопросов к аналитику/лиду |
| Spec / ticket (SDD) | **Да** | Человек утверждает spec |
| Реализация по утверждённому spec | **Да** | В рамках границ spec |
| Реализация без spec «сделай фичу X» | **Осторожно** | Разъезд ожиданий |
| Ревью и тесты | **Осторожно** | ИИ не снимает ответственность |
| Hotfix в прод без воспроизведения | **Нет** | Сначала стабилизация |

*В этом репозитории ориентир — [spec 0001](../specs/0001-task-keeper.md).*

**Проект:** [taskkeeper](https://github.com/dontagr/taskkeeper) — Go, `net/http`, POST/GET `/tasks`, in-memory storage, [spec 0001](https://github.com/dontagr/taskkeeper/blob/main/specs/0001-task-keeper.md).

**Зачем эта таблица:** на лабораторном примере видно, **какая строка матрицы за какой шаг книги отвечает**, и **какие задачи в рамках границ примера** можно отдавать ИИ, а какие — нет. Читатель может ориентироваться на эту таблицу при выполнении лабораторных заданий и в реальной работе.

**Границы примера (из spec, не-цели):** нет auth, БД, update/delete, поиска, OpenAPI. Всё, что туда лезет из промпта, — красный флаг (см. [историю 1](#история-1-блокировка-от-идеи-до-распределённого-ада) про «улучшения» вне контракта).

### Что на Task keeper не отдавать ИИ «на автопилоте»

| Соблазн модели | Строка матрицы | ИИ | Почему в рамках учебного примера |
|----------------|----------------|-----|----------------------------------|
| JWT / OAuth «для надёжности» | Реализация auth | **Осторожно** | Прямое нарушение не-целей spec |
| Postgres / Redis «вместо memory» | Дизайн схемы БД; интеграция SDK | **Осторожно** | Вне scope; усложняет лабу |

| «Улучшить архитектуру» (DI, 10 пакетов) | Выбор архитектуры; рефакторинг через пакеты | **Осторожно** | Достаточно `httpapi` + `storage` + `task` |
| Отключить тесты / линтер | Красные флаги (ниже) | **Нет** | — |

## Красные флаги (остановиться и не применять ответ как есть)

- Ответ уверенный, но **нет ссылок на ваш код/версии**
- Предлагает **отключить** тесты, линтер, security checks
- **Большой дифф** без объяснения побочных эффектов
- Меняет **auth, crypto, billing** «для простоты»
- «Так принято в индустрии» без учёта **ваших** conventions
- Вы **не можете воспроизвести** и объяснить изменение коллеге

### История 1. Блокировка «от идеи» до распределённого ада

**Задача:** ручка отправки push-уведомления; при двойном клике не должно быть дубля — нужна блокировка на время отправки.

**Что сделал с ИИ:** описал сценарий «требуется реализовать механизм блокировки от параллельного вызова на время отправки уведомлений». Модель выдала простую схему: `SET` блокировки, по завершении `DEL` по тому же ключу. На одной ноде выглядит разумно.

**Где сломалось бы в проде:** приложение крутится **больше чем на одной ноде**. Нода A взяла lock, отправляет push, TTL истекает. Нода B успевает взять lock на тот же ключ. Нода A закончила работу и **без зазрения совести удаляет ключ** — снимает чужую блокировку. Дубли и гонки снова в игре; в логах это ловится плохо.

**Что спасло:** не merge «как есть», а **ревью с уточнением контекста**: несколько инстансов, TTL, кто и когда снимает lock (только владелец, lease, Redlock / аналог по вашему стеку). Исправили до выката.

**Урок:** строки вроде *«Интеграция с незнакомым SDK»*, *«Рефакторинг через несколько пакетов»* — про **скрытый контекст**. ИИ не угадывает топологию кластера, если вы её не сказали. Для таких задач матрица даёт **Осторожно** минимум; при деньгах/уведомлениях/идемпотентности — ближе к **Нет** без spec и ревью с человеком, который видел прод.

### История 2. План, spec и загрузка файла в БД

**Задача:** сервис загрузки данных из файла в базу — объёмная фича, легко утонуть в «сделай всё сразу».

**Как работал с ИИ:** не один промпт «напиши сервис», а цепочка:

1. **Brainstorming** — разобрать цель, риски, границы (скиллы из [superpowers](https://github.com/obra/superpowers) удобны именно для этого).
2. **Writing-plans** — пошаговый план.
3. Мои **коррективы в план:** загрузка **асинхронная**, файл разбирается потоково, в БД — **пакетные** вставки; отдельно прописал **правила валидации строк** файла.
4. Итоговый план **сохранил как spec** к проекту и шёл по пунктам, а не по «вдохновению модели».

**Итог:** реализация шла итерациями; правки после агента были **минорные** — потому что спорили с планом до кода, а не с диффом на 3 000 строк после.

**Урок:** строки *«Spec / ticket (SDD)»* и *«Реализация по утверждённому spec»* — **Да**, если spec ваш и вы его держите в контексте. Строка *«Реализация без spec „сделай фичу X“»* — как раз антипаттерн, от которого ушли.

### История 3. Spec из уже живого кода (и эталон DDD)

**Задача:** не выдумывать spec с нуля, а **зафиксировать**, как у вас уже принято в коде — чтобы новые микросервисы не плодили «зоопарк».

**Как работал с ИИ:**

1. Дал на анализ **существующий** репозиторий: «какие архитектурные решения здесь видны?» — слои, границы пакетов, где домен, где адаптеры.
2. Если в команде **ещё не** дожили до hex/DDD, но **хотите** — ничто не мешает взять **эталон** (например [go-ddd](https://github.com/sklinkert/go-ddd)) и попросить: «сверь с этим образцом, предложи структуру для сохранения в spec».
3. Результат — **базовая spec-скелет** микросервиса: слои, именование, куда класть handlers/storage, что в не-цели.

**Итог:** один раз согласовали с командой **базовую spec**; дальше новые сервисы — копия структуры + доменные разделы, а не «как модель решила в этот вторник».

**Урок:** *«Написать README / комментарии»*, *«Spec / ticket»* — **Да** для **черновика** и инвентаризации. *«Выбор архитектуры»*, *«Дизайн схемы БД»* — **Осторожно**: ИИ подсказывает паттерн, **решение и эталон** — за вами. Spec из кода — ускоритель; spec **вместо** разговора с командой — ловушка.

### История 4. Painless в Elasticsearch, когда дока «не щёлкает»

**Задача:** написать скрипт на **Painless** для Elasticsearch — обход вложенных объектов в документе, нужная логика в update/search pipeline (конкретный контекст — ваш mapping и поле).

**Что было без ИИ:** официальная документация есть, но **сходу собрать рабочую конструкцию** не вышло — синтаксис Java-подобный, а семантика своя: как итерировать `Map`/`List`, что можно в `ctx._source`, где падает на nested, отличия версий ES.

**Что сделал с ИИ:** описал **структуру документа** (кусок JSON), версию Elasticsearch и что должно получиться на выходе. Попросил не только «дай скрипт», а **объясни конструкции**: `for`, доступ к полям, когда нужен `def`, типичные ошибки Painless.

**Итог:** черновик скрипта + разбор «почему так» — за вечер вместо долгого тыканья по форумам. Довёл на **dev/staging**: `_scripts` / sample docs, смотрел `_explain` или логи при ошибке компиляции скрипта.

**Урок:** это зона **Да** из таблицы «Общее»: *«Выучить концепт»*, и из dev — условно *«Регулярки, парсинг простого формата»* / незнакомый мини-DSL: **низкая цена ошибки**, если не гоняете скрипт сразу в прод без прогона. ИИ здесь — **репетитор + черновик**, не замена [доки Painless](https://www.elastic.co/guide/en/elasticsearch/reference/current/modules-scripting-painless.html): финальную версию сверьте с версией кластера и прогоните на реальных mapping. Для **массовых** update в проде — уже **Осторожно**: нагрузка, идемпотентность, откат.
