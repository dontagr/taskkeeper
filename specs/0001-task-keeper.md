# Spec 0001: Task keeper (save + get task)

**Дата:** 2026-05-27  
**Автор:** Сергей Степовой  
**Статус:** draft  

---

## 1) Контекст

Мы пишем мини‑сервис **Task keeper** на Go как сквозной пример для книги: HTTP API на `net/http`, 2 эндпоинта (сохранение и получение), in‑memory storage, unit‑тесты.

Цель примера — показать путь «чат → системная работа → SDD», без “магии одним промптом”.

---

## 2) Цель

Сделать минимальный HTTP API, который позволяет **сохранить** задачу и **получить** задачу по id.

**Definition of Done (DoD):**

- [ ] Реализованы 2 эндпоинта: create + get
- [ ] Есть in-memory storage
- [ ] Ответы и ошибки соответствуют spec
- [ ] Unit‑тесты покрывают happy path + ключевые edge cases
- [ ] `go test ./...` проходит
- [ ] Код отформатирован `gofmt`

---

## 3) Не‑цели

- Не делаем аутентификацию/авторизацию
- Не делаем БД/персистентность на диск
- Не делаем обновление/удаление
- Не делаем поиск/фильтры/пагинацию
- Не делаем сложные статусы/приоритеты
- Не делаем генерацию OpenAPI

---

## 4) Требования (functional)

- R1: Сервис принимает создание задачи и возвращает созданный объект с `id`.
- R2: Сервис отдаёт задачу по `id`.
- R3: При запросе несуществующей задачи возвращает 404.
- R4: При невалидном вводе возвращает 400 с ошибкой в JSON.
- R5: Сервис потокобезопасен для конкурентных запросов.

---

## 5) API

### 5.1 Create task

**POST** `/tasks`

**Request JSON:**

```json
{
  "title": "Buy milk"
}
```

**Rules:**

- `title` обязателен
- `title` после `strings.TrimSpace` должен быть длиной 1..200

**Response 201 JSON:**

```json
{
  "id": "t_000001",
  "title": "Buy milk",
  "createdAt": "2026-05-27T19:00:00Z"
}
```

### 5.2 Get task

**GET** `/tasks/{id}`

**Response 200 JSON:** как объект выше.

---

## 6) Ошибки (единый формат)

Все ошибки возвращаем в JSON:

```json
{
  "error": {
    "code": "invalid_argument",
    "message": "title is required"
  }
}
```

**Коды:**

- 400 `invalid_argument` — невалидный JSON / невалидные поля / пустой `title`
- 404 `not_found` — task с таким `id` нет
- 405 `method_not_allowed` — если метод не подходит (по возможности)
- 500 `internal` — unexpected

---

## 7) Модель данных

### 7.1 Task

- `id` — строка, генерируется сервисом
- `title` — строка
- `createdAt` — RFC3339 timestamp в UTC

### 7.2 ID формат

Для примера делаем простой детерминированный формат:

- префикс `t_`
- 6 цифр с leading zeros: `t_000001`, `t_000002`, …

Требование: уникальность в рамках процесса.

---

## 8) Edge cases

- Create: пустой body → 400 `invalid_argument`
- Create: невалидный JSON → 400 `invalid_argument`
- Create: `title` пустой/пробелы → 400 `invalid_argument`
- Create: `title` > 200 → 400 `invalid_argument`
- Get: неизвестный id → 404 `not_found`
- Get: пустой id (например `/tasks/`) — поведение роутера; достаточно не поддерживать

---

## 9) Набросок реализации (technical design)

Рекомендуемая структура:

- `internal/httpapi` — handlers + routing (`net/http`)
- `internal/task` — доменная модель/валидация (минимально)
- `internal/storage` — in-memory store (map + mutex)

Потокобезопасность:

- storage держит `sync.RWMutex`
- create берёт `Lock`, get — `RLock`

Сериализация:

- `encoding/json`
- `createdAt` хранить как `time.Time`, в JSON отдавать как RFC3339 (стандартный marshal)

---

## 10) План тестирования

### 10.1 Unit: storage

- Create возвращает уникальные id по порядку
- Get возвращает сохранённый task
- Get несуществующего id → not found (ошибка)
- Потокобезопасность: базовый параллельный smoke (не гарантирует, но ловит грубые ошибки)

### 10.2 Unit/handler tests (через `httptest`)

- POST /tasks → 201 и корректный JSON (title, id, createdAt)
- POST /tasks с пустым title → 400 и формат ошибки
- GET /tasks/{id} после создания → 200 и корректный JSON
- GET /tasks/{id} неизвестный → 404 и формат ошибки
